# PortfolioSight demo implementation plan

**Normative spec:** docs/specs/2026-10-13-portfoliosight-demo-design.md (revision 2 plus §9.6). **Assertions:** docs/specs/2026-10-13-portfoliosight-demo-design.assertions.md (A-PS-01 … A-PS-68 in the machine gate; A-PS-69, a real browser through Cloudflare's Managed Challenge, is outside the manifest as the human-verification item H-PS-01, Phase 7 task 7.3). The spec is normative over this plan: on any conflict the spec wins and the plan is corrected. Workers read the phase's `Spec:` sections in full BEFORE implementing; the assertions are only the mechanical done-floor, the spec's §Expectations define done, and the plan is a route, not a substitute.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task inside the conductor recipe below. Steps use checkbox (`- [ ]`) syntax for tracking. Each phase is executed by a fresh agent with no memory: everything it needs is in this file, the spec sections the phase names, and the repo.

**Goal:** Ship `https://portfoliosight.ai` in private preview: a one-screen efficient-frontier page with a diversification heatmap, two sliders, presets, custom menus, three themes, nightly data from Tiingo and tsp.gov into R2, a FastAPI build service on KS-001 behind cloudflared, and a Cloudflare Worker front door, with every §11 definition of done demonstrated by a smoke test from the laptop.

**Architecture:** Python engine (pure functions, cvxpy + Clarabel) precomputes a tensor per (universe, lookback); the browser only interpolates (§4.11). Data flows laptop lake → R2 seed → Tiingo/tsp.gov tails → R2 canonical store; KS-001 is stateless (300 MB cache). Reads go Worker → R2; only `POST /api/tensors`, `/api/health` and R2 misses reach KS-001 through the tunnel, authenticated by `x-ps-gate`. Cloudflare Managed Challenge is the only human check; §9.6 private preview sits in the Worker until the owner buys the commercial license.

**Tech stack:** Python 3.12, numpy, pandas, pyarrow, scipy, scikit-learn, cvxpy ≥ 1.5, clarabel, pydantic, boto3, exchange_calendars, FastAPI, uvicorn; Vite 7, React 19, TypeScript 5.8, D3 modules, zod, vitest, Playwright; Cloudflare Workers (static assets, R2 binding, Durable Object), wrangler; Docker Compose + systemd on KS-001.

**Spec:** docs/specs/2026-10-13-portfoliosight-demo-design.md

## Per-phase recipe (every phase, no exceptions; referenced by each phase below)

A fresh subagent implements the phase on a phase branch forked FROM THE RUN BRANCH (`git checkout -b feature/<phase-slug> <run-branch>`; never from `main`) → `/code-review` per task, reviewed against the phase's `Spec:` sections and `ADRs:` (not just the diff) → commit per task → one PR per phase with base = the run branch, body containing `Closes #<phase-issue>` → opposite-host review ×2 by **codex**: each one a read-only, pre-merge review of PR#<pr> against the phase's `Spec:` sections and ADRs, run through the Codex review wrapper that `conductor preflight` names, posted as PR comments carrying the gate's review marker (`CONDUCTOR_REVIEW_MARKER`, default `Codex review`); findings are applied with `receiving-code-review`, committed, and the final state is re-reviewed by codex until the last review postdates the last commit and raises nothing blocking → `conductor merge-gate` → `conductor merge <pr>` into the run branch → `/document-release` → `conductor ledger phase-done <phase-issue> --plan docs/plans/2026-10-13-portfoliosight-demo-plan.md`.

Test scope per task is the focused test file for what the task changed plus lint/typecheck on touched files; the full suite runs once per phase inside the merge gate. The gate tests under `assertions/2026-10-13-portfoliosight-demo-design/` are frozen and are never edited; a red assertion turns green by implementing the product. Before the first task of every phase the subagent reads `assertions/2026-10-13-portfoliosight-demo-design/INTERFACES.md` (run rule 11) and the gate test files for the phase's ids, so it builds to the names the gate calls. ## Global constraints (from the spec; every task inherits them)

- Python ≥ 3.12 (`python:3.12-slim` image, §9.1); engine version `0.1.0` (§7); generation id `{D_G}-{engine_version}` (§5.3).
- Libraries: numpy, pandas, scipy, scikit-learn (`LedoitWolf`), cvxpy ≥ 1.5 with Clarabel (§4); `yfinance`, `matplotlib`, `plotly`, `skfolio` only in the `research` extra (§12 Step P); no provider other than Tiingo and tsp.gov; no EODHD, Schwab or yfinance calls anywhere in runtime code (§2, §5.1).
- Tolerances, one rule: `|Σw − 1| ≤ 1e-6`, `min − 1e-6 ≤ w ≤ max + 1e-6`, `σ(w) ≤ X + 1e-6`, `1 − 1e-6 ≤ ENB ≤ N + 1e-6`; Clarabel `1e-8`; tensor floats at full `repr` precision (§4.11, §7).
- Grid `NX = 48`, `NY = 32`; the only fallback is `NX = 32`, `NY = 24`, applied once after measuring (§4.12).
- Caps `min = 0`, `max = clamp(3/N, 0.25, 1.0)`; validation `0 ≤ min ≤ max ≤ 1`, `Σmin ≤ 1 ≤ Σmax`, `N ≥ 2`; 2–30 funds per menu (§4.4, §6).
- Lookbacks `1y=252, 2y=504, 3y=756, 5y=1260, 10y=2520, ew` (half-life 252); inclusion `first return ≤ window_start + 0.10·len`; sample floor 126 rows; served = `last_date ≥ D − 3` and `adjusted_through ≥ D − 3` trading days (§4.2, §5.2).
- Copy: never "bets", "knee", "Sharpe", "tangency", "covariance", "sigma", "quantile", "significant" in default copy; never "you should", "we recommend", "Risk Number", "Risk Score"; the HUD theme is called "HUD" and references no film, character or trademark (§3.6, M6).
- Tests: `tests/` mirrors the package; `web/tests/` for vitest; `web/e2e/` for Playwright; scripts in `scripts/`; no network except tests marked `live` (skipped unless `PS_LIVE_TESTS=1`); ≥ 80% Python line coverage, 100% on `portfoliosight/engine/` (§10).
- `data-testid`s exactly as listed in §10; themes `ks-dark|light|hud` with the §3.5 token table verbatim.
- Secrets and hygiene per run rule 4; `.dockerignore` and image contents per §5.3 and A-PS-32.

## Review focus (spec-implied inputs no task's tests otherwise exercise; each line names the owning task that pins it)

1. A custom menu whose window intersection is below 126 rows for `5y` but fine for `1y` (a 2025 launch) must build `1y` and mark `5y` `unavailable` with "not enough shared history", not fail the POST → task 3.5 adds the per-window `unavailable` case; task 4.6 adds the API test that `POST` with `lookback: "5y"` for such a menu returns a 409-free `200`/`202` for `1y` and a clear `422 invalid_request` with `details.reason = "not enough shared history"` for `5y`.
2. A current mix whose entire weight sits in excluded funds (e.g. a custom menu whose only amount is on FIENX) must not divide by zero: no current-mix marker, Trades hidden, a one-sentence note → task 3.5 (renormalize returns `None` and the set-aside share 1.0) and task 5.9 (Funds note "The mix you entered uses only funds set aside in this view").
3. A tensor key whose `generation.json` is missing because the nightly pruned the generation between POST and build → task 4.5: the job fails with error code `generation_gone`, `retry: false`, and the client's 409 handling (task 5.5) shows the error code and offers the presets.
4. The URL `r=` outside the domain after a lookback switch (the domain differs per tensor) → task 5.4 clamps on every tensor load, not only on first decode, and task 5.5 re-applies `d=auto` when the clamped `s` changes.
5. A share request whose `url` is valid but longer than 2,048 characters after re-encoding (30 funds with amounts and caps) → task 5.12: the Worker re-encodes first and refuses on the re-encoded length with `400 invalid_url`, and the dialog disables "Send" with "This view is too long to email; copy the link instead" before the request.
