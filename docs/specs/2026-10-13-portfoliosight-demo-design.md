# PortfolioSight demo: design spec

Date: 2026-10-13, revision 2 (after Codex review round 1). Status: approved for build. Owner: Jeff Daniels. Repo: `github:automateintelligence/portfoliosight`.
Inputs: `docs/reviews/2026-10-12_strategy_memo_portfolio_risk_return_website.md`, `..._addendum_user_feedback_and_decisions.md`, the six research reports, the owner's brainstorm decisions (final). The memo and addendum are historical context; where they differ from this spec, this spec is authoritative. This spec is consumed by an Expectations section (written afterwards), executable assertions, and an autonomous multi-phase build where each phase is done by a fresh agent with no memory. Every choice here is final unless a phase proves a sentence internally contradictory or physically impossible; the phase may then correct that sentence (never the Expectations section, the frozen gate or its interface pins, and never to make a failing test pass) in a commit of its own with a one-line note, reviewed with the phase. Anything larger blocks the phase with a written reason.

Owner's framing: "This is really not that complicated of a project, so don't over-complicate it. Build it out as a demo. If you build it wrong, we will fix it later. The goal is speed balanced with good econometrics and great website design and aesthetics."

## 1. Purpose and audience

A public page at `https://portfoliosight.ai`. A visitor sees a fund menu's efficient frontier, where a current mix sits against it, drags a risk slider, and gets a better-diversified mix at the same risk. Audience: people with a 401(k)/TSP/brokerage fund menu (NAVSEA/TSP friends first, Bogleheads-adjacent generally). Educational, impersonal, not advice. No login; the only gate is Cloudflare's standard human check.

## 2. Decisions and non-goals

Owner decision, 2026-10-13: the default menu's FIENX is replaced by EFA (iShares MSCI EAFE ETF, history from 2001), so the default view uses all 23 funds; FIENX stays in the tier 2 catalog as the example of a converted fund that is not served. The frozen gate was updated accordingly (`docs/reviews/2026-10-13_gate-change_fienx-to-efa.md`).

Owner decision, 2026-10-13: the default preset is displayed as "Example Portfolio". It is the 2017 guide's Step 2 allocation; its preset id `guide2017`, its holdings file and its URL value are unchanged, so shared links and stored data keep working. The frozen gate was updated accordingly (`docs/reviews/2026-10-13_gate-change_fienx-to-efa.md`, section "Preset display name").

Decided by the owner (not revisited here): first screen is the chart and its controls, everything else collapsed; no tangency/max-Sharpe point; risk slider = one-year range (bad and typical year; one year replaced six months by owner decision on 2026-10-13); a diversification control along the constant-risk-ceiling line defaulting to a suggested point; a diversification-surface heatmap under the frontier as the centerpiece; diversification in four plain words; presets (2017 guide Step 2 with allocation; TSP core funds) plus custom portfolios of up to 30 funds from the served universe; trade list; adaptive caps; lookbacks 1/2/3/5/10y + exponentially weighted with ghost frontiers; three stress cards; three themes (KnowledgeSight dark default, own light, HUD); plain-language layer; URL-encoded portfolios; Portfolio-Visualizer-style disclaimers; family footer CTA; backend precomputes, browser only interpolates; FastAPI container on KS-001 behind the existing cloudflared tunnel; Vite + React + TypeScript + D3 on Cloudflare Workers static assets; Cloudflare WAF Managed Challenge as the gate.

Data decisions (2026-10-13, owner-confirmed): the EODHD subscription does not include prices, dividends or splits, so the product uses **Tiingo** behind a small provider Protocol (one adapter; a second can be added later); no yfinance, no Schwab, no EODHD calls. The owner's QSE lake (working copy on the laptop's WSL disk at `~/tft-quantile-forecaster/data/tft/raw/eodhd/datalake_us_core/eod_history`, 1,445 symbols with back-adjusted `adj_close` through 2026-02-27; `/mnt/d/tft-quantile-forecaster` is only QSE's nightly mirror and may be unmounted) is used once as a **seed**, uploaded from the laptop; QSE's own storage layout is not changed. **Cloudflare R2 is the canonical store** (bucket `portfoliosight-data`), the laptop drive `/mnt/d/` is the backup, and the KS-001 container is stateless apart from a 300 MB cache; KS-001's disk will not be expanded. Secrets live in `~/.secrets/portfoliosight.env`. Production ingestion of provider data into R2 requires the owner's confirmation of a provider plan whose terms allow storing the data and derived outputs (§13, §9.5 step 3); writing the code does not.

Choices made in this spec where the owner left them open are marked **[choice]** with a one-line reason.

Non-goals (ROADMAP only, see Appendix B): FERS planner, risk questionnaire / risk number, hedge/collar calculator, emails, programmatic SEO pages, payments/paywall, accounts/login, copula Monte Carlo, Student-t toggle, image export, walk-forward UI, robustness score, more than 30 funds, tickers outside the served universe, exact-ENB (non-convex) optimization, a second price provider, a TSP preset with L Funds.

## 3. User experience

### 3.1 First screen

One viewport, no scrolling needed to use the product. Layout (desktop ≥ 1024 px):

```
┌ header: wordmark "PortfolioSight"  [preset ▾]  [share ⇪]  [theme ◐] ────────┐
│ ┌ chart (D3; canvas heatmap+frontier, SVG markers) ───────┐ ┌ div slider ┐ │
│ │  y: expected return (yr)                                  │ │ More return│ │
│ │  heatmap Z(risk ceiling, return floor) under the frontier │ │     ●      │ │
│ │  frontier line; vertical risk-ceiling line at X; point ●  │ │            │ │
│ │  current mix ◻ (if an allocation exists); ○ most diversif.│ │ More       │ │
│ │  x: risk (yearly ups and downs)                           │ │ diversified│ │
│ └───────────────────────────────────────────────────────────┘ └────────────┘ │
│  risk slider (one thumb, aligned with the risk axis)                         │
│  ◄──────────────────●──────────────────────►  Bad year −9.4% · Typical year +3.1% │
│  result strip: Selected mix  Bad −9.4% · Typical +3.1% · Good +15.6%   Diversification: Good  [details] │
│  chips: [Funds & amounts] [Stress tests] [Trades] [Settings]  (scroll to the collapsed sections) │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Funds & amounts sidebar (≥ 1024 px; owner feedback 1).** On every screen 1024 px or wider, Funds & amounts (§3.3) is a sidebar on the right of the first screen, beside the chart, the diversification slider and the result strip, so the table can be read while the chart is used. It is closed by default to a slim vertical tab that carries its name and an open icon; the tab, the "Funds & amounts" chip and "Custom…" in the preset menu open it, and the same button closes it. Open, it is 360 px wide (326 px between 1024 and 1279 px; owner direction 2026-10-13: the amount field needs room for "1,000,000" only, so the chart keeps the rest), the chart moves left and resizes, and the page's maximum width grows so a wide screen is used. Its body scrolls inside the first screen. Open or closed is remembered per browser (`localStorage("ps.funds")`). Under 1024 px there is no sidebar and Funds & amounts is the first collapsed section below the first screen, as before.

Chart contents, in draw order: (1) heatmap of Z over the grid of (risk, return floor) cells (canvas; each cell is drawn at its grid position and colored by the ENB of the most diversified mix found at that risk that earns at least that return, §4.7; in ks-dark, HUD and Grid the ramp runs against the measure, so the band along the frontier, where mixes are least spread out, is the brightest and the well-spread valleys below are darker: the frontier reads as a wall, not a cliff edge; in Light (owner direction 2026-10-13) the ramp runs with the measure, so the band along the frontier is the palest and the most spread-out mixes far below it are the deepest blue); (2) ghost frontiers (thin, 40% opacity, one per toggled lookback); every frontier line, the primary one included, carries a text label at its right end naming its history window ("1 year", "2 years", "3 years", "5 years", "10 years", "Weighted recent"), to the right of the line's end where there is room and above it otherwise (always above on a phone); labels that would touch are stepped apart and joined to their line by a short leader, the primary line keeping its place; with a mouse, a pointer within 7 px of a ghost line redraws that line at full strength and shows its name beside the pointer (the primary line needs none); (3) primary frontier (2 px): **one curve**, the locus of the interpolated frontier weights' actual (σ, μ) (§4.11), sampled at 8 sub-steps per column gap and passing through every grid node; (4) vertical dashed line at the selected risk ceiling X from the axis up to the frontier; (5) "most diversified" marker (small hollow circle) at the actual (σ, μ) of the column's most-diversified mix; (6) current-mix marker (hollow square) at its actual (σ, μ) when an allocation exists; (7) selected-point marker (filled circle with ring) at the selected mix's **actual** (σ, μ), which lies on or to the left of the ceiling line and, at the top of the diversification slider, exactly on the drawn frontier by construction; draggable (vertical drag = diversification slider, horizontal drag = risk slider); (8) individual fund dots with ticker labels only when details are on. **[choice]** Every mix is plotted where it really is and the line marks the ceiling (between grid nodes the frontier mix itself sits slightly left of the ceiling, which the tooltip explains), because re-parameterizing the grid on realized risk would cost a second solve pass for no product gain. No tangency point, no capital market line, no Sharpe anywhere. **Mix cards.** One card design names every mix the chart shows. The selected point, the square (the mix you entered) and the open circle (most diversified at this risk) each show it on hover, tap or keyboard focus: Low / Typical / High over six months, yearly risk and expected return (with the line "Risk and expected return are per year."), the diversification word, and the five largest holdings. The open card is the accessible description of the marker it belongs to. When the square and the circle sit on top of each other, a second tap or click turns the card over to the marker underneath, and the card says so. With a mouse, the colour map shows a smaller card for the mix at the cell under the pointer ("The mix at this spot": risk, expected return, diversification word, largest holdings); it gives way to a marker's card and to a ghost line's name. Default cards never mention a ceiling or a floor; with details on, each card adds the measure behind the word ("spreads risk over the equivalent of N independent bets; highest found on this menu: M") and the bell-curve figure, and the cell card adds where it was computed ("At risk X, earning at least Y"); every mix the sliders show sits exactly on the selected risk (Engine 2), so no card repeats its risk as a "ceiling".

### 3.2 Controls

- **Preset menu** (header): two ready-made portfolios and a custom option: "Example Portfolio" (the default view) and "TSP (G, F, C, S, I)", each loading in one click, plus "Custom…" (opens the Funds section).
- **Risk slider** (horizontal, under the chart, one thumb aligned with the chart's risk axis). Its parameter is the continuous column position `s` along the frontier curve over the domain `[s_safe, s_max]` (§4.9); the ceiling is `X(s)`. Two live readouts sit together beside the thumb and always move together: "Bad year −9.4%" and "Typical year +3.1%", the one-year range of the frontier mix at `s` (§4.9; "Best-return mix at this risk"). Risk and return are one position, so there is nothing to synchronize and no mode toggle. The readouts describe the **frontier** mix; the result strip describes the **selected** mix, which can differ once the diversification slider moves it down. Keyboard: arrow keys move 1/200 of the domain. If the domain collapses to a single point the slider is disabled with "this menu has only one sensible risk level".
- **Share** (header icon, and beside "Share this view" in Settings): a small dialog with "Copy link" (copies the current URL) and "Send by email" (recipient address, Send; §9.3). Status line: "Sent" / "That address doesn't look right" / "Too many shares for today".
- **Diversification slider** (vertical beside the chart on desktop, horizontal under the risk slider on phone). End labels "More return" (top/left) and "More diversified" (bottom/right). No percentages, no numbers, never the word "knee". It moves the selected point along the column at ceiling X between the frontier mix (top) and the column's most-diversified mix (bottom). Default position is the Optimized point (§4.8), which the chart marks with the open circle; the track carries no mark of its own (owner decision 2026-10-13: one open circle named "Optimized", no separate "Suggested" tick). A "Back to Optimized" link appears once the user moves it. When both neighbouring columns' ladders collapse (§4.11) the slider is disabled with the note "At this risk, the best-return mix is already the most diversified one found."
- **Result strip**: labelled "Selected mix": Bad / Typical / Good one-year return of the selected mix (§4.9; the label makes clear these can differ from the slider's frontier readouts once the diversification slider is moved down), on desktop a small bar drawing them (the Bad-to-Good band with end caps and the typical dot, 0% marked) on one fixed scale for the menu (the lowest Bad and highest Good over every mix the loaded tensors of every window carry, padded; it changes only with the menu), the diversification word (small, muted, not a headline; its caption bold in the strongest text colour), and a **details** toggle. Details on: the exact measure ("spreads risk over the equivalent of 3.8 independent bets; highest found on this menu: 5.1"; technical name "effective number of bets, minimum torsion"), yearly expected return and standard deviation of the selected mix (the standard deviation is the selected risk, so it is not repeated as a "risk ceiling"), lookback dates, "prices through {asof}", fund dots on the chart, and three explanations: what the diversification word means and what "Suggested" means, each in plain words (§3.6), then one "Method" line that states each technical rule once.
- **Theme switcher** (header): four-way segmented control, Dark (KnowledgeSight dark, the default) / Light / HUD / Grid, or one button that steps through the four in that order on a phone; persisted in `localStorage("ps.theme")`; the URL `t=` parameter wins over storage.
- **"Give us a moment"**: while a custom tensor builds, the chart area shows a centered notice with a progress ring and the queue position; controls are disabled; polling every 2 s. A failed build shows "We couldn't compute this menu" with a Retry button (re-POSTs the same request) and the server's error code; after three failures the notice says so and offers the presets. If any `/api/*` response carries `cf-mitigated: challenge`, the page keeps its state in the URL and performs a top-level reload so Cloudflare's interstitial can run, then resumes (builds are idempotent by generation, hash and lookback).

### 3.3 Collapsed sections (below the first screen, all collapsed by default)

Accordion sections in this order; chips on the first screen scroll to and expand the matching section. **[choice]** Sections further down the page rather than a drawer: one implementation works on every width and keeps the first screen clean.

1. **Funds & amounts** (a sidebar beside the chart from 1024 px, §3.1; this section below that): table of the menu: ticker, name, amount entered (number), then two percentage columns that are always shown whatever the unit: "Mix entered %" (the amounts as percentages of what was entered, blank when no amounts are entered or the percentages do not yet add up) and "Selected mix %" (the weights of the point selected in the chart, updating as either slider moves); status note for a fund the view sets aside (e.g. "converted to an ETF; no data since 2024-10-30: not used" for FIENX in a custom menu; the default menu has no such fund). A three-way unit toggle **Shares | % | $** applies to the whole table; the amount column is headed "Shares (Qty)", "Share (%)" or "Amount ($)". Input modes: tickers only (all amounts blank: no current mix, no Trades); tickers and share quantities (weights = shares × the fund's latest close on the generation date, `universe.funds[].last_close` in the tensor, §7); tickers and portfolio percentages (must add up to 100%: while the entries, as the fields show them to two decimals, do not add up to exactly 100%, a gentle warning shows the running total, e.g. "Total: 92%, 8% to go", beside a "Scale to 100%" button that rescales them in proportion to exactly 100 (largest remainder at the fields' precision; zeros stay zero); both are hidden at exactly 100%, with nothing entered, and in the $ and Shares units; no mix is plotted until the total is 100% ± 0.05); a "Clear all" button in every unit empties every amount and keeps the fund list (owner direction 2026-10-13); tickers and dollar amounts. Amounts apply as they are typed, and a one-line hint says so ("Amounts apply as you type."). Add fund (autocomplete over `/api/symbols`, which lists only served symbols; help text "Only funds and stocks with verified current data are offered."), remove fund. Adding or removing a fund changes a draft of the list; only while the draft differs from the list that is plotted, a "Recalculate with these funds" button is shown (it triggers the tensor fetch/build; disabled while percentages do not add up or the list has fewer than 2 or more than 30 funds). Max 30 funds; min 2. The Example Portfolio arrives in "$" mode with amounts from `data/holdings/holdings_guide2017_step2.csv` (Qty × Price); the TSP preset arrives blank. TSP L Funds are served and appear in the picker but are not a preset.
2. **Stress tests** (above Trades, owner direction 2026-10-13, so the cards sit near the chart on a smaller screen): three cards (§4.10). Under the big number the parenthetical reads "(Selected mix)" on every card, and the line for the mix you entered ("The mix you entered: −27.6%") is bold, label and number.
3. **Trades**: shown only when a current mix exists. Per fund: now %, selected %, change in percentage points, plus the change in dollars in "$" mode and the change in shares and dollars in "Shares" mode (`Δshares = round((w_sel − w_now) · V / last_close)`, `V = Σ shares · last_close`); "%" mode shows percentage points only. Totals: one-way turnover. Copy: "Moves to get from the mix you entered to the selected mix." An "Export CSV" button downloads the table from the browser (nothing is sent): one row per fund with any non-zero figure (held in either mix, or traded) with fund, now %, selected %, change in percentage points, plus the change in dollars in "$" and "Shares" modes and the change in whole shares in "Shares" mode; plain numbers; the file is named `portfoliosight-trades-{asof}.csv`.
4. **Settings**: lookback (radio: 1y, 2y, 3y, 5y (default), 10y, Weighted toward recent) with a list of funds excluded in that window and why; ghost frontiers (one checkbox per other lookback; each ghost can be toggled on and off again); caps table (min %, max % per fund, inline validation per §4.4, one-sentence rule explanation) with two buttons: "No limits" (every fund 0% to 100%, rebuilt like any cap change and carried in `c=` like any other cap) and "Reset limits" (back to the default rule); "Share this view" (copies the URL) with the share icon beside it (§3.2).

## 4. Econometric method

All engine code lives in `portfoliosight/engine/` (pure functions over numpy arrays; no I/O). The seed `portfoliosight/frontier_cli.py` stays unchanged as the research baseline. Libraries: numpy, pandas, scipy, scikit-learn (`LedoitWolf`), cvxpy ≥ 1.5 with Clarabel, threadpoolctl. **[choice]** cvxpy+Clarabel for the frontier: the risk constraint is second-order-cone and DPP-parametrized problems avoid re-canonicalization. The diversification ladders (§4.7) maximize the exact ENB, which is not convex, so they use scipy's SLSQP with an analytic gradient and several starting points.

### 4.1 From prices to returns

Per fund the store holds the canonical record of §5.3: raw daily `close` and a total-return index `tr_index`; the engine's daily return is always `r_t = tr_index_t / tr_index_{t−1} − 1`. Provider rows are turned into index increments with `div_cash` (cash distribution per share on its ex-date, including fund capital-gain distributions as the provider reports them) and `split_factor` (Tiingo: new shares per old share on the split date, 1.0 otherwise):

```
r_t = (close_t · split_factor_t + div_cash_t · basis_t) / close_{t-1} − 1 ;   tr_index_t = tr_index_{t-1} · (1 + r_t)
```

where `basis_t = split_factor_t` if the provider quotes `div_cash` per post-split share on a day with both actions, else 1. The adapter fixes `basis` by reproducing the provider's `adjClose` (fetched alongside, used only for validation) on recorded fixtures: AAPL around 2020-08-31 (4:1 split), NVDA around 2024-06-10 (10:1), USO around 2020-04-29 (1:8 reverse split), VTI and VBIAX full history (dividends and fund distributions); the adjClose ratio must match the built `tr_index` ratio to within 1e-5 per day on every fixture, and an agent never guesses the direction. Seeded rows take `tr_index` from the lake's back-adjusted `adj_close` (§5.4). TSP funds: share prices are already total-return NAVs, so `tr_index` is the price itself. Splice test: for VTI, a seed-style record cut at 2025-12-31 and a provider tail spliced from there must match the all-provider `tr_index` to within 1e-5 from 2026-01-02 on. Trading-day alignment: the universe calendar is the union of all funds' dates; a fund's return is NaN on days it has no price; window statistics use the intersection of dates where every included fund has a return.

### 4.2 Lookback windows and short histories

`asof` = `D`, a property of the **generation** (§5.3): the nightly computes `D_G` once as the most recent XNYS session (via `exchange_calendars`) whose close is at least 6 hours before the nightly's scheduled start (02:00 PT), records it in the generation's metadata, and every build in that generation, preset or custom, receives `D_G` as an argument and uses only price rows dated `≤ D_G`; it does not depend on which funds are included or on when the build runs. Window ids and lengths: `1y`=252, `2y`=504, `3y`=756, `5y`=1260, `10y`=2520 trading days ending at `D`; `ew` = the 5y window with exponentially decaying observation weights, half-life 252 days, applied by position. A fund is **included in a window** only if it is served (§5.2: price and corporate actions verified through `D − 3` trading days or later) and its first return date is on or before `window_start + 0.10 · window_length`. Excluded funds are listed in the tensor with a reason string and shown in the UI (§3.6). The window's sample is the intersection of included funds' dates; it must have ≥ 126 rows or the window is marked `unavailable` and the UI disables it with "not enough shared history". A current mix with weight in excluded funds is renormalized over included funds and the UI says what share was set aside.

### 4.3 Moments

- Annualization (annual units everywhere downstream): `μ_i = 252 · mean(r_i)`, `σ_i = √252 · sd(r_i)` (sample, ddof=1). For `ew`: weights `ω_t ∝ 0.5^{(T−t)/252}` normalized to sum 1, `mean = Σ ω_t r_t`, daily `S = Σ ω_t (r_t − mean)(r_t − mean)ᵀ / (1 − Σ ω_t²)` (weighted sample correction, so uniform weights reproduce the ddof=1 estimate exactly), `μ_i = 252 · mean_i`, `σ_i = √(252 · S_ii)`, effective sample size `T_eff = 1/Σω_t²`.
- Covariance, fixed windows: `sklearn.covariance.LedoitWolf` on standardized returns `r_i/sd(r_i)`; the estimate is renormalized to a correlation matrix (`R = Q / sqrt(diag Q diag Qᵀ)`) and rescaled with the annual variances: `Σ = D^{1/2} R D^{1/2}`, `D = diag(σ²)`. For `ew`: `R = corr(S)` shrunk with fixed intensity `R_s = 0.8 R + 0.2 I` (**[choice]** sklearn has no observation weights; a fixed intensity is adequate for a display window), then rescaled with the same annual `D = diag(252 · S_ii)`. **[choice]** Shrinking correlations rather than covariances so a near-zero-volatility fund (TSP G Fund, σ ≈ 0.3%/yr) keeps its own variance. Diagonal floor in annual units, `σ_i ≥ 1e-4` (0.01%/yr), applied to `D` before any factorization in both paths; test: the `ew` path on constant weights `ω_t = 1/T` reproduces the fixed-window `σ_i` within 1e-12.
- Expected returns, a **menu-beta heuristic** (**[choice]**, labelled as such): `μ_s = 0.5 · μ̂ + 0.5 · π`, `π_i = r_f + β_i · max(μ̂_eq − r_f, 0)`, `β = Σ w_eq / (w_eqᵀ Σ w_eq)`, `w_eq = 1/N`, `μ̂_eq = w_eqᵀ μ̂`. It scales each fund's premium by its beta to the equal-weighted menu, preserves the menu's average return (`w_eqᵀ π = w_eqᵀ μ̂` when the premium is positive), and when the menu's excess return is non-positive the **prior** `π` collapses to the cash rate (`π_i = r_f`) while the blended `μ_s = 0.5 · μ̂ + 0.5 · r_f` still carries half of each sample mean; the 50/50 blend is an arbitrary fixed intensity. Inspired by the no-views Black-Litterman prior (He & Litterman 1999) and by Kritzman, Page & Turkington 2010 on not using the raw sample mean; it is not a calibrated posterior. A cash-like fund is pulled toward `r_f`, not toward the equity average.
- Risk-free rate: trailing-12-month total return of SGOV if served, else TSP G Fund, else 0.04. One value per build.
- Citations: Ledoit & Wolf 2004 (JMA 88(2)); Jagannathan & Ma 2003 (J. Finance 58(4)); DeMiguel, Garlappi & Uppal 2009 (RFS 22(5)).

### 4.4 Caps

Default per-fund bounds: `min = 0`, `max = clamp(3/N, 0.25, 1.0)` with N the number of funds included in the window; so a five-fund TSP menu allows 60% in one fund, a 10-fund menu 30%, any menu of 12 or more funds 25%, and two- or three-fund menus are uncapped. This is an editable demo heuristic: a weight cap `c` only bounds weight concentration (`Σ w_i² ≤ c`, the DeMiguel, Garlappi, Nogales & Uppal 2009 norm-constraint idea) and says nothing about minimum-torsion concentration; 3/N keeps small menus usable. Validation on input (422 and inline in Settings otherwise): `0 ≤ min ≤ max ≤ 1` per fund, `Σ min ≤ 1 ≤ Σ max`, N ≥ 2. Greedy endpoint portfolios (§4.5, §4.7) allocate every fund's minimum first, then fill the remainder in `μ_s` order up to each maximum. The universe hash (§6) covers the **requested** cap policy (per-fund overrides, `null` when default), not the window-resolved bounds; each tensor records the resolved `bounds` it used.

### 4.5 Frontier

Grid of `NX = 48` risk columns `X_j` uniformly from `σ_min` (risk of the minimum-variance portfolio under bounds) to `σ_max` (risk of the max-return greedy portfolio under bounds). Frontier point at `X_j`:

```
maximize μ_sᵀ w   s.t.  ‖C w‖₂ ≤ X_j,  1ᵀw = 1,  min ≤ w ≤ max,   C = cholesky(Σ)ᵀ
```

NumPy's `cholesky` returns lower `L` with `Σ = L Lᵀ`, so `C = Lᵀ` and `‖Cw‖² = wᵀΣw` (unit test on a random SPD matrix). Outputs `y_front[j]` and `w_front[j]`; for `X_j < σ_max` the risk constraint binds, so frontier **nodes** sit on their ceiling (`σ(w_front[j]) = X_j` within 1e-6). One cvxpy `Problem` with parameters `(μ, C, X)` reused for all solves; Clarabel tolerances `tol_feas = tol_gap_abs = tol_gap_rel = 1e-8`, and the builder post-checks every returned weight vector against the 1e-6 invariants of §4.11 and raises otherwise.

Uncapped reference frontier: the same program with `min = 0`, `max = 1` for every fund, over its own 48 columns from its own `σ_min` to `σ_max`, stored as risk and return only (`frontier_uncapped`, §7) so the chart can show what the caps cost. Its feasible set contains the capped one, so it lies on or above the capped frontier everywhere.

### 4.6 Diversification measure and the four words

Measure: effective number of bets via minimum torsion (Meucci, Santangelo & Deguest 2015, "Risk budgeting and diversification based on optimized uncorrelated factors", SSRN 2276632). Port `torsion.m` (minimum-torsion, exact method, BSD) into `engine/torsion.py` as `min_torsion(Σ) -> T` (n×n, `T Σ Tᵀ` diagonal). Bet exposures, variance contributions and ENB for weights `w`:

```
b = T^{-T} w ;  Λ = diag(T Σ Tᵀ) ;  p_i = Λ_i b_i² / (wᵀ Σ w) ;  ENB(w) = exp(−Σ_i p_i ln p_i)  (p_i = 0 contributes 0)
```

`p_i ≥ 0` by construction; the builder asserts `max |offdiag(TΣTᵀ)| ≤ 1e-8 · trace` and `|Σp − 1| ≤ 1e-8` and raises otherwise (no silent clipping). Tests: diagonal Σ → `T = I`, inverse-volatility weights (`w_i ∝ 1/σ_i`) give `ENB = N`, and a single-fund portfolio gives `ENB = 1`; two uncorrelated funds with volatilities 10% and 20% at equal weight give `ENB = exp(−(0.2 ln 0.2 + 0.8 ln 0.8)) ≈ 1.649`; random SPD Σ → `TΣTᵀ` diagonal to 1e-8 and `Σp = 1`.

Words: `q = ENB(w) / enb_ref`, where `enb_ref` is the highest ENB among all mixes computed for this universe and lookback (every level of every column's ladder, §4.7, which include the frontier mixes and the peaks): "highest found on this menu", never "max" or "best possible". **[choice]** Good `q ≥ 0.75`, Average `0.50 ≤ q < 0.75`, Fair `0.30 ≤ q < 0.50`, Poor `q < 0.30`; relative to the menu's own reference because a five-fund TSP menu cannot reach the ENB of a 23-fund menu; the cut points are stated in the details footnote.

### 4.7 Diversification ladders at fixed risk

Every risk column `X_j` holds a **ladder**: mixes that all have exactly the column's risk, from the frontier mix at the top down to the most diversified mix found at that risk, the **peak**. Going down the ladder each level gives up some expected return and gains diversification; nothing below the peak is computed, because such a mix would earn less and be less diversified.

The program, for a column `X_j` and a return floor `Y`:

```
maximize ENB(w)   s.t.  σ(w) = X_j,  μ_sᵀ w ≥ Y,  1ᵀw = 1,  min ≤ w ≤ max
```

The peak drops the return floor. ENB is the exact minimum-torsion measure of §4.6, not a proxy; the program is not convex. **[choice]** It is solved with SLSQP (`scipy.optimize.minimize`, `ftol = 1e-9`, at most 200 iterations) in the coordinates `u = Λ^{1/2} T^{−T} w / X_j`, where the risk constraint is the unit sphere `‖u‖ = 1`, the bet shares are `p = u²/‖u‖²`, `w = X_j T^T Λ^{−1/2} u`, and the entropy's gradient is `∂H/∂u = −(2/‖u‖²) u (ln p + H)`; the bounds, the budget and the floor are linear in `u`. Every accepted mix is post-checked in weight space (§4.11) and must hold `|σ(w) − X_j| ≤ 1e-6`.

Search, per column, all of it deterministic (fixed seeds):
- **Peak.** Starts: the frontier mix; three random mixes on the risk line (each the average of three random greedy vertices of the bounded simplex, moved onto `σ = X_j`; generator seeded with `(20261013, j)`); and the best mix of the neighbouring column moved onto this column's risk line. Neighbouring columns then offer their best mixes to each other, sweeping in both directions until nothing improves.
- **Ladder.** `L = 12` interior return floors evenly spaced from `y_front[j]` down to the peak's return. Each floor is solved from three starts: the mix found at the floor above (continuation), the frontier mix and the peak. Every mix found at any floor of the column joins the column's pool; the level at floor `Y` is the pool's highest-ENB mix earning at least `Y` (the earlier-found on a tie). So, by construction, the return never rises and the ENB never falls down the ladder, and a mix found lower down that beats a level above replaces it. A level that beats the peak moves the peak and the ladder is laid out again (at most twice). After all ladders are solved, columns offer their peaks to their neighbours once more and a column that gains is laid out again.
- **Collapsed column.** When the pool's best ENB is within `1e-6` of the frontier mix's, every level is the frontier mix and `ladder.collapsed[j]` is true. When the best ENB is higher but costs no return (within `1e-6`), every level below the top is that mix.
- **Hops.** On some menus the set of mixes with risk exactly `X_j` and enough return is not connected, so the straight blend of two neighbouring levels can drop well below `X_j`. Where the midpoint blend of two levels loses more than 1% of `X_j`, `ladder.hop[j][l]` is true and the page never blends across that step (§4.11). On the fixture no column has a hop.

The search is a local method from several starting points, not a global optimum: the tensor's note says "the most diversified mix found". `enb_ref` is the highest ENB over all levels of all columns.

**Heatmap raster.** For drawing, the ladders are resampled, with no further solving, on `NY = 32` return floors `Y_k` uniform from the lowest peak return of all columns to `max_j y_front[j]` (`grid`, §7). Cell `(j, k)` holds the most diversified mix found at risk `X_j` that earns at least `Y_k`: inside the ladder's span (`y_peak[j] < Y_k ≤ y_front[j]`) the straight blend of the two ladder levels whose returns enclose `Y_k` (the upper level across a hop); at or below the peak's return, where the floor no longer binds, the peak itself; above `y_front[j]` the cell is `null` (nothing is feasible). `Z[j][k]` is the exact ENB of the cell's mix. Blends keep the risk at or below `X_j`, so a raster cell is drawn at its own actual coordinates like every other mix. `k_div[j]` is the highest row holding the peak (`−1` on a collapsed column), `y_div[j]` that row's floor (`y_front[j]` when collapsed) and `w_div[j]` the peak.

### 4.8 Suggested point: the balanced point or the peak

Each column's ladder yields two candidate defaults for the diversification slider, both stored in the tensor:
- **Balanced point**: the knee of ENB gained against return given up. Down the ladder, `g_l = (y_0 − y_l)/(y_0 − y_last)` is the share of the column's return span given up and `e_l = (z_l − z_0)/(z_last − z_0)` the share of its ENB gain reached; the balanced level maximizes `e_l − g_l`, which is the perpendicular distance above the chord from the frontier mix to the peak up to a constant factor (the earlier level on a tie). Between levels the curve is taken as straight, so the maximum is at a level. A ladder that gains no more than `1e-6` ENB answers level 0 (the frontier mix); one that gains ENB for no more than `1e-6` of return answers the last level (the diversification is free). Stored as `t_balanced[j] = l/(L + 1)` and `y_balanced[j]`.
- **Peak**: the last level.

A single build-time constant `DEFAULT_POINT` (`"balanced"` by default, or `"peak"`) chooses which one fills `t_suggested`/`y_suggested`, and the tensor records the choice in `ladder.default_point`. The rule needs no extra solves.

### 4.9 One-year range, risk slider domain

Every range is **one year**. For a mix `w` the engine computes:
- **Bootstrap range (bad / typical / good year).** The mix's daily returns over the window's own sample, `r_t = wᵀR_t`, are recentred so their mean is the expected return (`r_t − mean(r) + μ_sᵀw/252`), then resampled with the stationary block bootstrap (Politis & Romano 1994): 2,000 paths of 252 trading days, each built from runs of consecutive days whose lengths are geometric with mean 21 days, wrapping around the end of the sample. One index matrix, drawn from a fixed seed (`20261013`), is shared by every mix of a build, so ranges of different mixes are comparable and a rebuild gives the same numbers. Each path is compounded, `∏(1 + r_t) − 1`, and the 2.5th, 50th and 97.5th percentiles (linear interpolation) are the bad, typical and good year. Recentring fixes the daily mean, so the typical year sits near `e^{μ − σ²/2} − 1`, a little below `μ`. With 2,000 paths the Monte Carlo error of the 2.5th percentile is about `0.06σ`. For `ew` the expected return is the weighted one and the shape comes from the same five-year sample, unweighted (the tensor's notes say so).
- **Normal range.** `μ ± 1.96σ` around `μ`, with the mix's annual `(μ, σ)`, for comparison.

The engine computes both for every frontier node, every ladder level (so the peak and the balanced point too) and, when the build carries an allocation (presets), the entered mix. Ranges for any other mix (a custom menu's entered mix, a position between nodes) come from `POST /v1/range` (§6), which rebuilds the sample from the price records, checks that it is the build's to the bit (its SHA-256 over fund ids, days and every return must equal the tensor's `lookback.sample_sha256`) and uses the same index matrix; when the history behind a tensor has changed since its build, it refuses rather than answer from different data. The range computation sits behind one function, `portfoliosight.engine.ranges.one_year_ranges`, so the planned methods (filtered historical simulation, then copulas; ROADMAP) change no page code.

Planned successor (2026-10-14): `docs/specs/2026-10-14-portfoliosight-simulation-engines-design.md` specifies the selectable simulation engines (History replay, Volatility model, Copula) behind this function and the replacement of the §4.6 measure, after the minimum-torsion ENB was found inflated on correlated menus; that spec governs those topics once the owner approves it.

The risk slider's parameter is the continuous column position `s ∈ [0, NX−1]` (`j = ⌊s⌋`, `λ = s − j`, ceiling `X(s) = (1−λ)X_j + λX_{j+1}`); its readouts are the bad and typical year of the frontier mix, read between nodes by straight interpolation of the node values. The domain is `[s_safe, s_max]` with `s_safe` the **rightmost frontier node with the best bad year** (`frontier.s_safe`, an integer) and `s_max = NX−1`; positions left of `s_safe` have lower volatility but both lower return and a worse bad year, and are drawn but not selectable. The page reads `s_safe` from the tensor; it cannot recompute it (it has no return history). If `s_safe = s_max` the slider is disabled (§3.2). Initial `s` on load: the position whose ceiling `X(s)` equals the current mix's σ, clamped into the domain, if an allocation exists, else the domain midpoint. The selected mix's own range (result strip) is its own and can differ from the slider readout in either direction.

TSP G Fund: handled by the correlation-space shrinkage and diagonal floor (§4.3); its ENB and word are computed like any other mix (a single holding can load several minimum-torsion factors when it is correlated with the rest of the menu, so no identity is assumed). The details line for any mix whose σ is below 1% reads "there is little risk here, but it may all be in one place". No special-casing elsewhere.

### 4.10 Stress windows

Three fixed windows: `gfc2008` 2008-09-01 → 2009-03-09 ("2008 financial crisis"); `covid2020` 2020-02-19 → 2020-03-23 ("COVID crash, Feb–Mar 2020"); `rates2022` 2022-01-03 → 2022-10-12 ("2022 rate shock"). The tensor carries, per fund, the buy-and-hold total return over each window (`null` if the fund lacks a price within 3 trading days of both endpoints). The browser computes the selected mix's and the current mix's window return as `Σ_i w_i R_i / Σ_i w_i` over covered funds, shows the covered share, and, if covered weight < 50%, replaces the number with "Not enough of this mix existed then to say." Never fabricates.

### 4.11 Browser-side math and fidelity

The tensor ships `mu_s`, `sigma`, `cov`, `torsion` (T), `torsion_inv_t` (`(Tᵀ)^{-1}`) and `torsion_lambda` (Λ) so the browser computes exact `μ`, `σ`, ENB, the normal range and stress results for any weight vector; one-year bootstrap ranges come from the tensor at nodes and levels and from `POST /v1/range` for any other mix (§4.9). Interpolation for a slider position `(s, t)`, `t ∈ [0,1]` (0 = frontier mix, 1 = peak), `j = ⌊s⌋`, `λ = s − j`: for each of the two neighbouring columns, the ladder's `L + 2` levels sit at `t = l/(L + 1)`; `w_j(t)` is the straight blend of the two levels around `t`, except across a hop (`ladder.hop[j][l]`), where the upper level holds up to the middle of the step and the lower one from there on; a collapsed column returns its frontier mix for every `t`; the result is `w(s, t) = (1−λ) w_j(t) + λ w_{j+1}(t)`. The reference implementation is `portfoliosight.engine.surface.interpolate`. At a column (`λ = 0`) and a level, the mix is that level's mix, exactly on the risk line; between levels or columns the blend keeps `σ(w) ≤ X(s)` by convexity of the norm and sits slightly inside it. The frontier curve is `w_front(s) = w(s, 0)`; the chart draws its actual `(σ, μ)` sampled at 8 sub-steps per gap, so the selected point at `t = 0` lies on the drawn frontier by construction. No clipping and no renormalization: a convex combination of feasible weights satisfies the bounds and sums to 1. Statistics are recomputed from the tensor moments, never interpolated. The diversification slider's default is `t_auto(s) = (1−λ) t_sug[j] + λ t_sug[j+1]` with `t_sug[j] = ladder.t_suggested[j]` (0 for a collapsed column), so at a column it lands exactly on the suggested level. The ENB order of a ladder (never falling as `t` grows) holds at columns and levels by construction and is not guaranteed between them.

Tolerances, one rule everywhere (tensor floats are serialized at full double precision, §7; Clarabel at 1e-8, §4.5): the invariants are `|Σw − 1| ≤ 1e-6`, `min − 1e-6 ≤ w ≤ max + 1e-6`, `σ(w) ≤ X(s) + 1e-6`, `1 − 1e-6 ≤ ENB ≤ N + 1e-6`, checked by the Python builder on every solved vector and by the TypeScript tests on interpolated ones. Ladder levels must also hold `|σ(w) − X_j| ≤ 1e-6`. Fidelity tests: at every grid node, ladder level and frontier node the TypeScript `stats(w)` equals the Python values in the tensor to 1e-9 relative (same inputs, full precision; fixture `web/fixtures/guide2017_5y.json`); for 200 random `(s, t)` the invariants hold and `w(s, t)` equals the reference walk; `t = 0` reproduces `w_front(s)` and `t = 1` the interpolated peak; for a pair of collapsed ladders `w(s, t)` is constant in `t`.

### 4.12 Determinism and runtime

The engine's only randomness is seeded (the random starts of the peak search, §4.7, and the bootstrap's index matrix, §4.9), and BLAS runs on one thread during a build, so floating-point sums happen in the same order on every run. Determinism means the same inputs give the same output: building twice from the same price records, `D_G`, bounds and engine version yields identical canonical JSON after removing the telemetry fields `built_at` and `build_seconds` (test on the fixture). A generation pins only `D_G` and the engine version; custom tensors are built from the price records and served-status catalog **as of build time**, so two requests for the same (generation, menu, lookback) made before and after a refresh are not guaranteed identical. Each tensor therefore records `built_at` and every fund's `adjusted_through` and `fetched_at`, and the first tensor built for a key is the one served for the rest of that generation (keys are never overwritten). Solve counts per lookback: 48 + 48 conic frontier programs (capped and uncapped) and, for the ladders, about 2,000 small SLSQP programs (23-fund fixture: 2,064), plus the bootstrap, one `2,000 × T` count matrix times the `T × (mixes)` log-return matrix. Measured 2026-10-13, pinned to 2 CPUs on a development machine: the 23-fund fixture builds in about 3.7 s (5.8 s for the CLI including start-up; up to about 20 s when the machine is busy), a 5-fund menu in about 1.8 s. Runtime is a **benchmark, not a promise**: the target is ≤ 30 s for a 23-fund (universe, lookback) build and ≤ 3 min for a preset's six lookbacks on KS-001's 2-vCPU container, measured in Phase 4 and recorded in the runbook; the named fallback if the target is missed is fewer ladder levels (the host setting `PS_GRID_LEVELS`, default 12, never below 8), applied once and re-measured. CI asserts only that the 23-fund fixture builds in ≤ 90 s.

### 5.1 Price provider

    def fetch_daily(self, symbol: str, start: date, end: date | None) -> pd.DataFrame: ...
        # columns: date (index, tz-naive), close, adj_close, div_cash, split_factor; empty frame = no data

The provider fills the canonical record (§5.3) for (a) symbols not in the seed (every mutual fund, the curated ETFs the lake lacks), fetched in full; (b) the corporate-action **tail** of seeded symbols from `adjusted_through` forward; (c) nightly updates. For (b) and (c) the adapter is called with `start = adjusted_through − 7 days`, the rows are converted with §4.1 and spliced onto the stored index at `adjusted_through` (continuity `tr_index_t = tr_index_{adjusted_through} · Π(1 + r_s)`), after which `adjusted_through = last fetched date`. A seeded symbol is never served before its first tail refresh, because unknown splits in a price-only tail would fabricate crashes.

### 5.3 Storage: Cloudflare R2 is the canonical store; KS-001 is stateless

Owner decision (final): no universe data lives on KS-001; R2 is canonical, the laptop drive `/mnt/d/` is the backup. A dedicated bucket **`portfoliosight-data`** (new; the account's existing buckets `knowledgesight-documents`, `olney-forms`, `qse-backup`, `scs-backups`, `scs-models` are not reused), accessed with the S3-compatible API (`boto3`, `endpoint_url=https://{CLOUDFLARE_ACCOUNT_ID}.r2.cloudflarestorage.com`, `region_name="auto"`, credentials `CLOUDFLARE_R2_ACCESS_KEY_ID` / `CLOUDFLARE_R2_SECRET_ACCESS_KEY`). `portfoliosight/data/store.py` wraps get/put/list/delete with retries and is the only code that touches R2; `LocalStore` with the same interface backs tests and local development (`PS_STORE=r2|local`, `PS_LOCAL_STORE_DIR`).

Key layout (a **generation** `G = {asof}-{engine_version}`, e.g. `2026-10-12-0.1.0`, is immutable once published):

```
prices/{SYMBOL}.parquet            canonical per-symbol record (below); TSP as TSP-G.parquet etc.
meta/manifest.json                 mutable catalog, per symbol: name, kind (etf|mutual_fund|stock|tsp), tier, income, source
                                   (seed|tiingo|tsp|seed+tiingo|lake), first_date, last_date, adjusted_through,
                                   status (ok|pending|stale|unavailable), reason, fetched_at,
                                   relies_on_yfinance (bool, false by default; §5.4)
meta/lake.json                     the lake sync's overlay, written by it only: {"generated_at" (the lake run synced),
                                   "synced_at", "symbols": {id: manifest entry + "digest"}}
meta/symbols.json                  mutable catalog view: exactly the body of GET /api/symbols; rewritten whenever the manifest changes
meta/provider_limits.json          measured plan and limits in force (§5.2)

meta/current.json                  {"generation": G, "published_at"}: the single pointer, switched last; its switch is the only publication marker
meta/{G}/generation.json           immutable, written once when the generation's inputs are fixed: G, asof (= D_G), engine_version, bounds rule,
                                   lookback definitions, created_at (its existence means "inputs fixed", never "published")
meta/{G}/presets.json              immutable, written once after all preset tensors exist: exactly the body of GET /api/presets for generation G
meta/status.json                   last nightly run: started, finished, D_G, symbols refreshed per tier, errors
tensors/{G}/{hash}/{lookback}.json preset and custom tensors of generation G, never overwritten
```

Generation metadata is immutable and written once; the symbol catalog is mutable and separate, so a visitor sees new symbols as they become served without any generation changing, while every tensor in `G` is pinned to `D_G`.

Canonical per-symbol record (**[choice]** raw close plus a total-return index: the seed has `adj_close` but no dividend records, the provider has both; one format both fill): parquet columns `date` (tz-naive), `close` (raw), `tr_index` (1.0 on the first row, dividends reinvested at the ex-date close, splits removed), `div_cash` and `split_factor` (nullable; provider rows only, for audit). Daily returns are always `tr_index.pct_change()`. Rows after `adjusted_through` are price-only and are never served (§5.2).

Repo files (committed, read-only at runtime): `data/universes/tiers.json`, `data/universes/portfoliosight.txt`, `data/universes/qse_core.txt`, `data/presets.json`, `data/holdings/holdings_guide2017_step2.csv`. Personal holdings files and research runs are gitignored and purged from history; `.dockerignore` excludes `runs/`, `data/holdings/*` except the Step 2 CSV, `.venv`, `web/node_modules`, `web/dist`, and a test asserts the built image contains none of them.

KS-001 scratch: the container keeps a size-capped LRU cache at `/app/cache` (named Docker volume `ps-cache`, owned by the image's `app` user, uid 10001; `PS_CACHE_MAX_MB=300`, evicted by last access after every build and every nightly step); it holds only the parquet files a build needs and the tensor being written. Nothing on KS-001 is authoritative.

Backup and restore (owner's laptop): `scripts/r2_backup.sh` mirrors the bucket to **`/mnt/d/portfoliosight-data/`** with the AWS CLI v2 (`aws s3 sync --endpoint-url https://{ACCOUNT}.r2.cloudflarestorage.com s3://portfoliosight-data /mnt/d/portfoliosight-data --delete`), reading the two R2 keys from `~/.secrets/portfoliosight.env`. Before syncing, the script checks `mountpoint -q /mnt/d` and that `/mnt/d/portfoliosight-data` exists or can be created; if D: is not mounted it prints "D: drive is not mounted at /mnt/d; backup not run" and exits with status 2 (never a silent skip). `scripts/r2_backup.sh --restore` runs the same sync with source and destination swapped (laptop → bucket, never `--delete` on restore), with the same mount check. The KS-001 container never sees `/mnt/d/`. Phase 4 schedules the backup in the laptop's WSL crontab next to the existing 05:00 QSE backup: `30 5 * * * $HOME/programming/portfoliosight/scripts/r2_backup.sh >> $HOME/.local/state/portfoliosight/r2_backup.log 2>&1` (added idempotently by `scripts/install_backup_cron.sh`, which leaves every other crontab line untouched). A run with D: unmounted logs the message, exits 2, and the next run catches up. Restore is only ever run after the bucket is confirmed lost or corrupted.

### 5.4 Seed, catch-up and nightly

**Seed (one-time, laptop → R2, zero provider cost).** `python scripts/seed_r2_from_lake.py [--lake PATH] --adjusted-through 2026-03-27 [--dry-run]` reads the lake's per-symbol parquet from `--lake`, which defaults to the WSL working copy `~/tft-quantile-forecaster/data/tft/raw/eodhd/datalake_us_core/eod_history` (`/mnt/d/tft-quantile-forecaster` is only QSE's nightly mirror and may be unmounted, so it is never the default); the script exits with a clear error if the path does not exist or holds fewer than 1,000 parquet files. Columns `date, open, high, low, close, adj_close, volume`; 1,445 files, 269 MB. It converts each to the canonical record (`tr_index = adj_close / adj_close.iloc[0]`, price-only after `adjusted_through`) and uploads `prices/{SYMBOL}.parquet` plus manifest entries with `source: seed`, `adjusted_through: 2026-03-27`, `status: pending` (8 concurrent uploads, resumable by skipping keys that already exist with the same size). The lake's `dividends/` and `splits/` folders are empty and ignored. Before uploading anything the script asserts that no row after `--adjusted-through` in any file has `adj_close != close` and prints the latest per-symbol adjustment date it found (expected: VTI 2025-12-19, AAPL 2026-02-06, SGOV and TLT 2026-02-27); a violation stops it.

Correction (Phase 0, 2026-10-13): the dry-run over the real lake found the four expected dates above, but also 295 symbols with `adj_close != close` after 2026-02-27; the lake's latest adjustment is 2026-03-27, so `--adjusted-through 2026-02-27` is refused and the seed command above now says 2026-03-27, the latest adjustment date the dry-run reports (on that day: 1,400 symbols to seed, 5 not seedable); the four dates above stay as per-symbol expectations, and manifest entries carry `adjusted_through: 2026-03-27`.

**Lake sync (laptop → R2, each weekday, zero provider cost; owner decision 2026-10-15).** The owner's QSE lake is repaired (`adj_close` back-adjusted from its `dividends/` and `splits/`, each row with a `source`: eodhd, yfinance or schwab) and refreshed each weekday, so it keeps stocks current without the Tiingo budget. `scripts/sync_lake.py [--lake PATH] [--dry-run] [--force]` reads `~/tft-quantile-forecaster/data/tft/raw/eodhd/datalake_us_core/` and never writes it, nor takes QSE's pipeline lock (it has its own lock under `~/.local/state/portfoliosight/`).

- *When.* QSE's price stitch (weekdays 06:45 PT) rewrites every price file, then `_adjusted_through.json` (`{"generated_at", "method", "symbols": {id: date}}`) last; a lake run is complete for today when `generated_at`, compared as a timestamp, is at or after today 06:45 America/Los_Angeles. Cron runs the sync weekdays every 10 minutes from 07:00 to 09:50 PT (`scripts/install_sync_lake_cron.sh`); it waits (exit 0) until the run is complete, syncs it once (the `generated_at` synced is recorded in `meta/lake.json`, so later polls do nothing), and at the 09:50 poll, if the run is still not complete, logs a line starting `ALERT sync_lake` and exits 1 without uploading anything. Saturday and Sunday it exits 0 at once. `--force` syncs the lake run there is, whatever the day, time or previous sync. `--dry-run` prints the counts and writes nothing.
- *Which symbols.* Each symbol of tiers 1–3 (TSP aside) is taken when the lake holds it, vouches it (a date under `symbols`; omitted symbols are not vouched), that date is its last price row, and the date is within 3 sessions of the latest vouched date in the file (so a weekend or holiday drops nothing, and symbols that stopped in March are not taken). Precedence: a tier 1 or tier 2 fund that a provider already keeps (source `tiingo`, `seed+tiingo` or `tsp`, status not `unavailable`) stays the provider's, so the presets keep their source; the lake wins for tier 3 stocks and for any symbol no provider has refreshed (`seed`, absent, or `unavailable`).
- *What it writes.* For a taken symbol whose lake files (`eod_history`, `dividends`, `splits`) and vouched date have changed since the last sync (sha256 digest), `prices/{SYMBOL}.parquet` in the canonical record (`tr_index = adj_close / adj_close[0]`, the seed's conversion); with the symbols about to change claimed first in `meta/lake.json` (their current dates, an empty digest), so a provider walk running then neither fetches them nor writes over them (the walk also re-reads `meta/lake.json` before each request and each record write, and writes the manifest conditionally too); a record that cannot be stored keeps its claim, the run logs `ALERT sync_lake` and is not recorded as synced, and the next poll stores it; then `meta/lake.json`; then `meta/manifest.json` by a conditional read-modify-write (R2 `If-Match`; a write that lost to another writer is re-read and retried, so a nightly write is never overwritten); then `meta/symbols.json`. A taken entry has `source: lake`, `last_date = adjusted_through =` the vouched date, the catalog's name (the lake has no names, so a stock is listed by its ticker), `kind` from the universe files (`stock` for tier 3), status by the date rule of §5.2 against `D_G`, and `relies_on_yfinance`: true when any dividend or split row dated after 2026-03-20 has a `source` other than `eodhd` or `schwab` (today that is `yfinance`; an allow-list, so a new source is flagged too). A symbol the sync took before and no longer takes is released: its entry becomes `source: seed`, `pending`, verified through its last vouched date, and the provider may take it over from there.
- *yfinance.* The owner accepts the lake's yfinance-sourced dividends for the private preview (decision 2026-10-15). **Before public launch, review symbols with `relies_on_yfinance`** (drop them, or have the provider refresh them).

**Downloader.** `python -m portfoliosight.data.download --mode measure-limits|catch-up|refresh [--symbols ...] [--tiers 1,2,3]`, run as a one-shot container job on KS-001 (or on the laptop with the same env file). Catch-up: for every symbol of the configured nightly set without a record, fetch the full history and its meta (two requests); for every `pending` seeded symbol in that set, fetch the tail (one request) and splice. Refresh: for **every** symbol of the configured nightly set, whatever its status, fetch from `adjusted_through − 7 days` (one request; §5.1) and splice; a symbol is skipped only when both `last_date ≥ D_G` and `adjusted_through ≥ D_G`, so a seed with recent prices but unverified corporate actions is always refetched from its adjustment date. Both walk the priority order of §5.2, write each symbol's parquet as they go, recompute each symbol's status against `D_G`, and rewrite `meta/manifest.json` and `meta/symbols.json` atomically after each tier (the nightly and the lake sync are their only writers; each applies the sync's `meta/lake.json` just before it writes the manifest, so neither drops the other's entries; a symbol whose entry says `source: lake` is never fetched). A symbol whose record cannot be stored once the store's retries are spent (R2: 8 attempts with backoff) is recorded as that symbol's error (`provider: store` in `meta/status.json`) and keeps its previous record and entry; the walk goes on, and publication still depends only on the preset tensors. The ledger `meta/budget.json` counts requests per UTC hour and day and unique symbols per month; the downloader sleeps to the next hour when the hourly budget is spent and exits cleanly when the daily or monthly budget is spent.

**Nightly** (host timer on KS-001, §9.1, every day at 02:00 PT; each step reads and writes R2): (1) compute `D_G` per §4.2 and `G = {D_G}-{engine_version}`; if `meta/current.json` already points at `G`, skip to step 4 (published); (2) refresh tier 1 (23 provider requests + the TSP CSV); (3) write `meta/{G}/generation.json` if absent, build every preset tensor (two presets × six lookbacks, with `D_G`) whose key is missing under `tensors/{G}/…` (a rerun after a failure resumes here), verify by `head_object` that all 12 keys exist, write `meta/{G}/presets.json` if absent, then switch `meta/current.json` to `G` (publication happens only after the completeness check; readers never see a half-built generation; nothing under `meta/{G}/` is rewritten); (4) refresh tier 2 `income`, rest of tier 2, tier 3 slice within budget, rewriting the catalog as symbols change status; the step stops between symbols at a deadline, the first instant after the run's start that is 30 minutes (`PS_NIGHTLY_DEADLINE_MINUTES_BEFORE_NEXT`) before a scheduled 02:00 PT start, records `deadline` and `stopped` in `meta/status.json` (not as an error), and leaves the rest to the next run, so a long walk never makes systemd skip the next start (steps 2 and 3 have no deadline); (5) delete every generation older than the previous one (custom tensors live and die with their generation); (6) write `meta/status.json`; (7) evict the cache to its cap. Alerts: none for the demo; `/v1/health` exposes `meta/status.json` and `D_G`.

### 5.6 Missing-data policy

A fund that is not served, or has too little history for a window, is dropped from that computation and listed with its reason in the tensor's `excluded` array; the UI shows the note in the Funds table and the Settings lookback list. Nothing is interpolated, back-filled or fabricated. Reason strings are fixed templates: `no data`, `converted to an ETF; no data since {date}`, `no data since {date}`, `corporate actions not yet verified after {date}`, `history starts {date}, not enough for the {window} view`.

Universe hash: `sha256(canonical_json({"schema":2,"funds":[{"id","min","max"} sorted by id]}))[:16]` over the **requested** policy (`min/max` `null` when default). Build queue: a single worker thread inside the API process with a job table keyed by `(G, hash, lookback)`; a POST for an existing key returns its state instead of enqueuing; only the requested lookback is built (other lookbacks build on demand when selected; the page requests them as the visitor switches); a job that raises is marked `failed` and a later POST re-enqueues it up to 3 attempts; a build reads `meta/{G}/generation.json` for `D_G`, reads only the needed `prices/*.parquet` and the catalog as they are at build time from R2 into the cache, uses rows `≤ D_G`, records `built_at` and per-fund `adjusted_through`/`fetched_at` in the tensor, writes it to `tensors/{G}/…`, and never overwrites an existing key (§4.12). `G` is read from `meta/current.json` at POST time, so a job started before a nightly switch completes in its own generation with its own `D_G`, and the client, which holds `G`, keeps working. `POST /v1/range` rebuilds the tensor's lookback sample from the price records the first time a tensor is asked about (the returns are never shipped to the browser) and keeps the 8 most recently used samples in memory, so a later request costs one matrix product. Abuse protection: input limits above; per-IP limiter keyed by `CF-Connecting-IP` (5 `POST /v1/tensors` per minute, 60 requests per minute on `/v1/*` including `POST /v1/range`, 429 otherwise); `uvicorn --limit-concurrency 32`; request body limit 16 KB; plus the Cloudflare rate-limiting rule of §9.4.

## 7. Tensor format

Floats are serialized at full double precision (Python's shortest round-trip `repr`, the default of `json.dumps`), never rounded, so the browser recomputes from exactly the solver's numbers and the single tolerance rule of §4.11 applies unchanged. Sizes: N = 23 → about 750 KB raw, roughly 290 KB gzip-compressed; N = 30 → about 1 MB raw.

`universe.excluded` is empty for the default menu, whose 23 funds are all used; a menu that holds a fund the view cannot use lists it there, e.g. `{"id": "FIENX", "reason": "converted to an ETF; no data since 2024-10-30", "last_close": null}` (§5.6). `asof` is the generation's `D_G`; `last_close` is the fund's raw close on `D_G` (the browser converts share quantities to weights with it; `null` when unknown). `ladder` holds each column's `L + 2 = 14` levels (§4.7): level 0 is the frontier mix, the last the peak, level `l` sits at `t = l/13`; `y`, `z` are each level's return and ENB, `hop[j][l]` marks a step that must not be blended, `collapsed[j]` a column whose frontier mix is the most diversified mix found. `t_balanced`/`y_balanced` are the balanced point, `t_suggested`/`y_suggested` the default position chosen by `default_point` (§4.8). `frontier.range` and `ladder.range` are the one-year ranges of every frontier node and every level, `entered` the menu's own allocation (presets only; `null` otherwise) renormalized over the included funds with its set-aside share and ranges, and `range_method` the bootstrap's parameters (§4.9). `frontier.s_safe` is the rightmost node with the best bad year. `frontier_uncapped` is the uncapped reference frontier's risk and return (§4.5). `lookback.sample_sha256` is the SHA-256 of the window's sample (fund ids, days, every daily return as little-endian doubles, in order); it lets `POST /v1/range` prove it answers from the build's own sample and reveals nothing about the returns. `grid` is the heatmap raster of §4.7: `grid.w[j][k]` and `grid.z[j][k]` are `null` outside a column's ladder; `k_div[j] = -1` marks a collapsed column; `w_div[j]` is the peak; `y_sug[j]` repeats the suggested return (the raster floor `y_div[j]` when the suggestion is the peak) for older readers and will be dropped. `frontier_curve` holds the actual `(σ, μ)` of `w_front(s)` at 8 sub-steps per gap (377 points for 48 columns), used for drawing; it is derived data (recomputable from `frontier.w` and the moments; the TypeScript tests assert equality to 1e-9 relative) shipped so the chart needs no startup computation. The tensor never carries fund-level daily returns. Fund order is the `universe.funds` order everywhere. A JSON Schema at `portfoliosight/engine/tensor.schema.json` is the contract; the Python builder validates on write and the TypeScript loader on read (`zod`).

### 8.1 URL encoding

Query parameters, all optional, updated on every change: `u` preset id (`guide2017|tsp`) or omitted for custom; `f` custom funds as `ID:amount` comma-separated (amount optional, e.g. `f=VTI:60,BND:40,VNQ`); `unit` `pct|usd|shares` (default `pct`); `c` cap overrides `ID:min:max` (percent integers; blank = default); `lb` lookback id; `g` ghost ids comma-separated; `r` risk slider position `s` as a decimal (e.g. `r=19.25`, clamped into the domain on load); `d` diversification position `auto` or a decimal in `[0,1]`; `t` theme id (`ks-dark|light|hud|grid`; `t=hud` is the red and gold HUD); `x` `1` when details are on. Example: `https://portfoliosight.ai/?u=guide2017&lb=5y&r=19.25&d=auto&t=hud`. Decoding never trusts the URL for anything but these fields; unknown funds are reported through the normal 400 path.

### 9.4 Human check, origin authentication and smoke-test exemption (standard Cloudflare only)

Rate-limiting rule (Free plan: one rule, expression fields limited to path and verified bot, 10 s period, 10 s block): `ps-tensor-post`, expression `(http.request.uri.path eq "/api/tensors")`, 20 requests per 10 s per IP, action Block; it matches the exact POST path and not the `GET /api/tensors/{G}/…` polling paths; POST-specific limits are enforced in the application (§6). Browsers never send the header and get the Managed Challenge on first visit, after which the `cf_clearance` cookie covers the page and its same-origin `/api/*` fetches; when clearance expires mid-session a fetch receives the challenge page, which the client detects by `cf-mitigated: challenge` and recovers from with a top-level reload (§3.2). Playwright smoke tests set `extraHTTPHeaders: {"x-ps-gate": process.env.PS_GATE_SECRET}` and pass both rules; the "unexempted request is challenged" test uses a fresh, cookieless request context without the header and expects HTTP 403 with `cf-mitigated: challenge` on `/`, and HTTP 403 without that header on `https://api.portfoliosight.ai/v1/health`. The API token in `~/.secrets/portfoliosight.env` currently lacks Zone WAF permissions (rulesets listing returns "Authentication error"), so the rules are created in the dashboard or after the owner adds `Zone › Zone WAF › Edit`; the secret is generated once (`openssl rand -hex 24`), stored as `PS_GATE_SECRET` in `~/.secrets/portfoliosight.env` on the laptop and on KS-001, and never committed.

- **Mutual-fund coverage**: verified for VTSAX, VBIAX, VGSTX, FXAIX, SWTSX; some curated tickers may 404 and are marked unavailable; FIENX (converted to an ETF) is in the catalog as not served and is not in the default menu, where EFA holds its place (§2).
- **tsp.gov**: the CSV requires a browser-like User-Agent and may change format; the parser asserts the exact header and the nightly marks TSP stale (not failed) if the fetch breaks.
- **Proxy vs. measure**: the surface optimizes weight concentration and reports exact ENB, which is not monotone along a column; the UI promises only what §4.7 states.
- **Runtime**: about 1,050 solves per lookback; the 30 s target is measured on KS-001 with one named fallback (§4.12).
- **KS-001 memory**: 1.5 GB limit; a build loads at most 30 symbols (< 10 MB); the nightly streams one symbol at a time. Shared with production KnowledgeSight services; the nightly runs at 02:00 PT.
- **Managed Challenge on phones**: some visitors see an interstitial; accepted by the owner. If Cloudflare changes the `cf-mitigated` header, DoD 2 and the client detection are adjusted, not the gate.
- **Workers Free quota**: 100k requests/day; every request runs the Worker (`run_worker_first: true`); a demo will not approach it.
- **Outbound email**: `POST /api/share` is the one place the site sends anything outward. It sends a fixed template to one visitor-supplied address, from `portfoliosight@automateintelligence.ai`, capped at 3 per IP and 50 globally per day, which bounds abuse to at most 50 unsolicited messages a day and keeps the domain's sender reputation (shared with the sibling sites) intact; the cap values live in `wrangler.jsonc` vars and can be lowered to 0 to switch the feature off without a code change.
- **Cloudflare token scope**: WAF rules may have to be created in the dashboard; tunnel ingress needs sudo on KS-001; the R2 keys may be scoped to other buckets (§9.5 step 1).
- **Seed quality**: the lake's `adj_close` is trusted as EODHD's back-adjustment through 2026-03-27 (the lake's latest adjustment, §5.4); the seed assertion, the VTI splice test and the first tail refresh (which revalidates corporate actions from that date) are the checks. A symbol whose seed history looks wrong is deleted from R2 and refetched in full from the provider.
- **R2 as a single point of truth**: a lost bucket is restored from `/mnt/d/portfoliosight-data/` with `scripts/r2_backup.sh --restore`; between backups, at most one night's deltas are lost and are refetched by the next refresh.

## Expectations

Written in the owner's voice. **[J]** marks an expectation taken from what the owner said; **[+]** marks one added for clarity and build quality. These define done; the sections above say how. Where the two disagree on what the visitor experiences, this section wins.

**What this is for.** A free demo I'd be glad to link from AutomateIntelligence: someone with a 401(k) or TSP menu opens it and, inside a minute, sees something about their mix they didn't know. One customer is a win. Speed matters more than polish in the plumbing, and wrong things get fixed later, but it must not embarrass me or mislead anyone.

### Success scenarios

- **S1 [J]** The page opens on a striking chart: a frontier with a colored map under it. Not a table, not a form, and nothing to fill in first.
- **S2 [J]** It works with nothing entered. The Example Portfolio and its allocation are already showing. TSP is a second ready-made portfolio that loads in one click.
- **S3 [J]** There is one risk slider under the chart. I drag it and understand it: it shows what a bad six months and a typical six months look like, both at once, and both change together because risk and return are one position. The point moves and the figures follow without a wait.
- **S4 [J]** A second, separate slider moves the point up and down at that risk level, between more return and more diversified. It starts at the suggested spot, and I can always get back there.
- **S5 [J]** The colored map shows at a glance where mixes are more spread out, and a visitor can tell what the colors mean without instructions.
- **S6 [J]** Diversification is stated as Good, Average, Fair or Poor, as a quiet label, not a headline.
- **S7 [J]** Every label on the first screen can be read by an average 401(k) holder. Technical names appear only when I ask for details.
- **S8 [J]** The tables (funds and amounts, trades, stress tests, settings) exist but stay out of the way until I ask for them.
- **S9 [J]** I can enter my funds four ways: tickers only; tickers and share quantities; tickers and percentages, which must add up to 100% and the page tells me when they don't; or tickers and dollar amounts.
- **S10 [J]** If I entered amounts, I can see what to move to get from my mix to the selected one. If I entered tickers only, there is no trade list.
- **S11 [J]** I can build my own menu from the funds offered, up to 30. If it takes time, the page says to give it a moment and then shows the result.
- **S12 [J]** The limits on how much one fund can hold make sense for the size of the menu: a five-fund TSP menu is not held to the same ceiling as a 23-fund menu, and I can change them.
- **S13 [J]** I can choose how many years of history to use (1, 2, 3, 5, 10, or weighted toward recent), overlay the others faintly, turn those overlays off again, and switch which one is primary.
- **S14 [J]** I can see what the selected mix did in 2008, March 2020 and 2022.
- **S15 [J]** There are three looks: the KnowledgeSight dark default, a separate clean light one, and a heads-up-display one. Each looks designed on purpose, the chart included, and my choice is remembered.
- **S16 [J]** On a phone, everything on the first screen works with a thumb and nothing scrolls sideways.
- **S17 [J]** The address in the browser always describes exactly what I'm looking at, and opening it elsewhere shows the same view.
- **S18 [J]** A share icon lets me email that link to an address I type. The message comes from portfoliosight@automateintelligence.ai.
- **S19 [J]** The only gate is Cloudflare's own "verify you are human" check. No login.
- **S20 [J]** It is live at portfoliosight.ai, refreshes itself nightly without me, and tests in Chrome against the live site demonstrate each item here.
- **S21 [J]** The data lives in R2 with a backup on my laptop drive. If the drive isn't there, the backup says so loudly and catches up next time.
- **S22 [+]** The figures agree with each other: the result strip, the chart, the trade list and a shared link all describe the same mix.
- **S23 [+]** Every mix shown is real: it adds to 100%, respects the limits, uses only funds in the menu, and is drawn where it actually sits.
- **S24 [+]** When something isn't available (a fund too new for the chosen history, a stock not yet refreshed), the page says so in one sentence and carries on with the rest.

### Failure scenarios (looks right, is wrong)

- **F1 [J]** The first screen reads like an engineering dashboard: tables, forms, dense numbers.
- **F2 [J]** Jargon leaks into the default view ("bets", "knee", "Sharpe", "tangency", "sigma"), or a tangency point is drawn.
- **F3 [J]** The suggested mix piles into one or two funds because of recent returns: the "85% in a hedged Japan fund" problem.
- **F4 [J]** The diversification word turns into a big score.
- **F5 [J]** The HUD look names or imitates the film, the light look is just KnowledgeSight's light theme, or a theme only recolors the background and leaves the chart unreadable.
- **F6 [J]** The phone version is the desktop page shrunk.
- **F7 [J]** There are separate risk and return sliders that drift apart, or a return figure that doesn't move when the risk slider does.
- **F8 [+]** Dragging a slider lags or jumps because the page is waiting on the server.
- **F9 [+]** The "more diversified" end isn't actually more diversified than the "more return" end, or the word contradicts what the slider just did.
- **F10 [+]** History is made up: a stress result for funds that didn't exist, missing dividends making a bond or cash fund look flat, a stock split shown as a crash, or one fund silently swapped for another.
- **F11 [+]** The page reads as personal advice ("you should", "we recommend", anything about age or goals).
- **F12 [+]** It works for the test browser but a real visitor gets stuck at the human check, or the page stops loading data once that check expires.
- **F13 [+]** The nightly refresh stops and the page keeps showing old numbers as if current.
- **F14 [+]** The default portfolio works but TSP or a custom menu errors or spins forever.
- **F15 [+]** The email share can be used to send someone a message of the visitor's own wording, a link to another site, or mail in bulk.
- **F16 [+]** The tests pass by checking that things exist rather than that they behave.

- **M4 [J]** Never build our own human check, and never add a login.
- **M5 [J]** Never store the universe data on KS-001, grow its disk, or starve the other services running there.
- **M6 [J]** Never name or reference the film, its characters or trademarks, and never use the words "Risk Number" or "Risk Score".
- **M7 [+]** Never fabricate, interpolate or back-fill data to make a chart look complete.
- **M8 [+]** Never present any output as advice or a recommendation, and never hide the disclaimer.
- **M9 [+]** Never disable, skip or weaken a test to get a phase through.
- **M10 [+]** Never build past the demo: no pension planner, questionnaire, hedging calculator, scheduled emails, payments or accounts.
